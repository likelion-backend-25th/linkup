## 1.1 인증 보안: HTTP Header를 통한 사용자 ID 전달 문제

### 1.1.1 문제 상황

- **문제 유형 (핵심 태그)**: 인증, 보안, JWT, 사용자 인증
- **어떤 기능에서 문제가 발생했는가?**
  - 팔로우 기능 구현 과정에서 로그인한 사용자의 ID를 HTTP Header로 직접 전달받는 방식으로 구현되어 보안상 문제가 발생
  - HTTP Header는 클라이언트에서 임의로 변경할 수 있어 다른 사용자의 ID를 전달하는 것이 가능했음

### 1.1.2 원인 분석

- 회원 로그인 기능이 구현되기 전 테스트를 위해 HTTP Header로 사용자 ID를 전달하는 임시 방식을 사용
- 이후 JWT 인증 기능이 구현되었음에도 기존 테스트 방식이 수정되지 않아 보안상 취약점이 남아 있었음

### 1.1.3 해결 방안

- HTTP Header를 통해 사용자 ID를 직접 전달받는 방식을 제거
- `@AuthenticationPrincipal CustomUserDetails`를 사용하여 JWT 인증 필터를 거친 검증된 사용자 정보를 전달받도록 수정
- 인증된 사용자의 ID를 기반으로 팔로우 기능을 처리하도록 변경하여 클라이언트에서 사용자 ID를 임의로 조작할 수 없도록 개선

## 1.2 OAuth 인증: 배포 환경의 카카오 로그인 Redirect URI 불일치

### 1.2.1 문제 상황

- **문제 유형 (핵심 태그)**: OAuth, 카카오 로그인, 배포, Redirect URI
- **어떤 기능에서 문제가 발생했는가?**
  - 배포된 프론트엔드 사이트에서 카카오 로그인을 시도할 때 `400 Bad Request` 오류가 발생
  - 로컬 환경에서는 정상적으로 카카오 로그인이 동작했지만 배포 환경에서만 로그인에 실패

### 1.2.2 원인 분석

- 카카오 로그인 과정에서 사용하는 Redirect URI가 실제 배포 환경과 일치하지 않는 문제 발생
- Kakao Developers에는 로컬 환경의 Redirect URI만 등록되어 있었고 배포된 프론트엔드의 Redirect URI가 등록되어 있지 않았음
- 이로 인해 배포 환경에서 카카오 인증이 완료된 후 정상적인 Redirect가 이루어지지 않아 `400 Bad Request` 오류가 발생

### 1.2.3 해결 방안

- Kakao Developers의 Redirect URI 설정에 배포 환경의 URL을 추가
- 로컬 환경과 배포 환경에서 사용하는 Redirect URI를 각각 등록하여 환경에 맞는 OAuth 인증이 가능하도록 수정
- 배포 환경의 Redirect URI를 등록한 후 카카오 로그인이 정상적으로 동작하는 것을 확인

## 1.3 파일 관리: 트랜잭션 롤백 시 실제 파일이 삭제되는 문제

### 1.3.1 문제 상황

- **문제 유형 (핵심 태그)**: 트랜잭션, 파일 삭제, 데이터 정합성
- **어떤 기능에서 문제가 발생했는가?**
  - 이미지 및 파일 삭제 기능에서 DB 데이터는 트랜잭션으로 롤백되지만 실제 저장소에 존재하는 파일은 롤백되지 않는 문제 발생
  - DB 데이터와 실제 파일 저장소의 상태가 서로 달라지는 데이터 정합성 문제 발생

### 1.3.2 원인 분석

- `@Transactional`을 사용하여 DB 작업은 롤백할 수 있었지만 실제 파일 저장소의 삭제 작업은 DB 트랜잭션에 포함되지 않았음
- DB 데이터 삭제 후 실제 파일을 먼저 삭제한 상태에서 이후 예외가 발생하면 DB는 롤백되지만 이미 삭제된 파일은 복구되지 않는 구조였음

### 1.3.3 해결 방안

- `TransactionSynchronizationManager`를 사용하여 실제 파일 삭제 작업이 트랜잭션이 정상적으로 커밋된 이후 실행되도록 수정
- DB 작업 중 예외가 발생하여 트랜잭션이 롤백되는 경우에는 실제 파일 삭제가 실행되지 않도록 변경
- DB 작업이 정상적으로 커밋된 경우에만 실제 파일을 삭제하도록 하여 DB와 파일 저장소의 데이터 정합성을 유지

## 1.4 구독 관리: 구독 해지 후 재구독 시 Duplicate 오류

### 1.4.1 문제 상황

- **문제 유형 (핵심 태그)**: 구독, 재구독, 데이터베이스, UNIQUE 제약조건
- **어떤 기능에서 문제가 발생했는가?**
  - 구독 해지 및 취소 시 기존 구독 레코드를 삭제하지 않고 `REMOVED` 상태로 변경하도록 구현한 후, 동일한 크리에이터를 다시 구독할 때 `Duplicate` 오류가 발생

### 1.4.2 원인 분석

- `creator_id`와 `member_id`의 관계가 `UNIQUE`로 설정되어 있어 동일한 회원이 동일한 크리에이터를 다시 구독할 수 없는 구조였음
- 기존 구독 데이터를 삭제하지 않고 `REMOVED` 상태로 유지하면서 새로운 구독 레코드를 생성하려 하자 기존 데이터와 동일한 `creator_id`, `member_id` 조합이 존재하여 `Duplicate` 오류가 발생

### 1.4.3 해결 방안

- `creator_id`와 `member_id`에 설정되어 있던 `UNIQUE` 제약조건을 제거
- 기존 구독 기록은 `REMOVED` 상태로 유지하여 구독 이력을 보존
- 재구독 시 새로운 구독 레코드를 생성할 수 있도록 데이터베이스 구조를 수정

## 1.5 관리자 신고 관리: 신고 처리 후 게시글이 삭제되지 않는 문제

### 1.5.1 문제 상황

- **문제 유형 (핵심 태그)**: 관리자, 신고 처리, 게시글 삭제, 트랜잭션
- **어떤 기능에서 문제가 발생했는가?**
  - 관리자가 신고를 처리하여 신고 상태가 변경되었음에도 신고 대상 게시글이 실제로 삭제되지 않는 문제 발생
  - 신고 처리와 신고 대상 삭제가 정상적으로 연계되지 않는 문제 발생

### 1.5.2 원인 분석

- 신고 처리 로직에서 신고 상태 변경과 신고 대상 삭제 로직이 분리되어 있었음
- 신고 대상이 게시글인지 댓글인지 구분하는 `target_type`에 따른 삭제 대상 처리 로직이 부족했음
- 신고 상태 변경만 정상적으로 처리되고 실제 신고 대상 삭제가 함께 수행되지 않는 구조였음

### 1.5.3 해결 방안

- 신고 유형인 `target_type`에 따라 신고 대상의 ID를 구분하여 실제 삭제 대상 ID를 조회하도록 서비스 로직 수정
- 신고 상태 변경과 신고 대상 삭제를 하나의 트랜잭션으로 처리하도록 변경
- 신고 처리 과정에서 하나의 작업이라도 실패할 경우 전체 작업이 롤백되도록 하여 신고 상태와 게시글 데이터의 일관성을 보장
